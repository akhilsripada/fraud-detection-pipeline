      How a swipe gets decided

      The same code runs on a laptop with one command, or serverless on AWS with Kinesis, Lambda and DynamoDB.

      1. Swipe arrives

        Each authorization lands on a stream, partitioned by card so one cardholder's events stay in order.

        Kinesis or in-memory

      2. Profile lookup

        The card's history: usual spend, last location, known devices and countries, recent charges.

        DynamoDB, optimistic locking

      3. Features

        Fifteen signals, like distance from the last swipe, travel speed, charges in the last minute, and spend versus normal.

        streaming, O(1) per event

      4. Model and rules

        Gradient-boosted trees score the risk. Rules add plain-English reasons and hard overrides, such as impossible travel.

        0.27 ms at p99

      5. Decision and alert

        Approve, hold or decline. A decline texts the cardholder “was this you?”, and their answer freezes the card or clears it.

        exactly-once alerts

      Measured, not promised

      Precision94.0%of flagged transactions were fraud, on held-out data
      Recall87.5%of fraud was caught

      Throughput6,600+ per secondon a single CPU core, p99 0.27 ms per transaction

      What's inside

      Streaming pipeline

      Python with no third-party dependencies. Per-card state, idempotent processing, and a config-driven rules engine.

      AWS, as code

      CDK stack with Kinesis, Lambda, DynamoDB, API Gateway WebSockets, SNS, Firehose and S3, plus CloudWatch metrics.

      AI you can talk to

      Plain-English questions are answered from the decision's real features. An MCP server lets Claude, ChatGPT or Cursor query the live stream.

      Cardholder experience

      A “was this you?” alert with the store, exact coordinates and local time, and an AR view that points the phone at where it happened.
